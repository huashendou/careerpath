## 二、设计原则

1. **每个技能只属于一个维度。** 雷达图按维度聚合，技能跨维度会造成同一能力被重复计数。
2. **每个技能至少被一个岗位引用。** 否则学生评了却不影响任何结果，属于自评空转。这条原则直接导致本版删掉了 12 项技能（见第八节）。
3. **等级用行为锚定，不用形容词。** 「精通 Python」无法验证，「独立做过完整模块、能自己排查常见报错」可以验证。
4. **权重合计固定 100。** 好处是可以直接读出「这一项占总分 9%」，比抽象的相对权重更好解释。
5. **结构可校准。** 校准时只换 `weight` / `target` / `type` 并升版本号，不动结构、不改前端。
6. **要求分两层：core 决定「够不够格」，plus 决定「有没有余量」。** 两者合起来才是完整岗位画像（合计 100），但只有 core 参与匹配度——理由是 plus 的定义就是「没有也能干」，把它算进分母等于把「没有也能干」变成「没有就扣分」，自相矛盾。第 6 条是本轮修订的核心。

## 三、六个通用能力维度

选六个而不是五个或八个，原因有两条：雷达图超过六轴会难以辨认；少于五个则区分不出三个岗位的结构差异。

| 维度 | id | 覆盖内容 | 为什么单独成为一个维度 |
|---|---|---|---|
| 编程基础 | `foundation` | 语言语法、并发/异步、数据结构与算法、网络与操作系统 | 面试第一关，也决定「能不能自己啃下新技术」的上限 |
| 岗位技术栈 | `stack` | 该岗位主流框架、库与工具链 | 岗位间差异最直观的一维，决定入职能否直接上手 |
| 工程实践 | `engineering` | Git、测试、调试、部署、性能、安全、接口联调 | 校招最高频的差距：会写功能，不会交付可维护的东西 |
| 数据与存储 | `data` | SQL、数据库、建模、清洗、采集 | 三个岗位都要读数据，只是深度不同 |
| 分析与洞察 | `insight` | 统计、指标体系、漏斗、可视化、报告 | 区分「会取数」与「能给出结论」，分析师的核心 |
| 交付与协作 | `delivery` | 需求理解、文档、沟通、团队推进、项目交付 | 技术相近时，决定录用的是这一维 |

### 故意不设的维度

- **「学习能力」单独成维**：无法通过自评可靠测量，且容易变成所有人给自己打 4 分。
- **「英语」单独成维**：对三个岗位都不是筛选门槛，放进维度会虚增雷达图形状。

## 四、0–5 级行为锚定

自评时以「最高一档能拿出证据的级别」为准。这条规则是整套模型可信度的地基——如果学生按感觉打分，后面的匹配度就没有意义。

| 级别 | 标签 | 判定锚点 | 典型证据 |
|---|---|---|---|
| 0 | 未接触 | 没学过，也说不清它解决什么问题 | 简历上不该出现这个词 |
| 1 | 听过概念 | 看过教程或文档，能解释是什么，没动过手 | 上过课、看过视频，写过 hello world |
| 2 | 跟做完成 | 跟教程或模板完整做过一遍，脱离教程要频繁查资料 | 课程作业、跟练项目，能跑通但说不清原理 |
| 3 | 独立完成 | 不靠教程独立做出完整模块或项目，能自己排查常见报错 | 课程设计、个人项目、竞赛作品的主要实现者 |
| 4 | 工程实践 | 在实习或多人协作的真实项目里用过，处理过边界情况、性能或线上问题 | 实习中负责过模块，代码被 review 并上了线 |
| 5 | 精通可教 | 能设计方案取舍、优化性能、指导他人，踩过深坑并有系统总结 | 能做技术选型、写团队规范、带新人 |

岗位目标等级统一按「校招 / 实习（初级）」设定，最高只到 4，没有岗位要求应届生达到 5。

## 六、计分口径（core-only）

### 6.1 两个量必须分开说

| 概念 | 口径 | 数值 |
|---|---|---|
| **完整岗位模型权重** | core + plus | 100（三岗都是 100） |
| **基础匹配度分母** | 仅 core 的 `Σ(w × T)` | 前端 255 / Java 294 / 分析 292 |

「100」是岗位画像的刻度，不是匹配度的分母。UI 上必须分开呈现：权重条可以显示「该技能占总分 9」，但匹配度百分比内部只用 core。否则用户会以为 plus 也进了那 100 分。

### 6.2 基础匹配度

```
M_core = Σ_core( w_i × min(L_i, T_i) ) / Σ_core( w_i × T_i ) × 100%
```

- `w_i`：core 要求的权重，**原值，不归一化**。
- `T_i`：岗位目标等级。
- `L_i`：有效等级（见 6.6 anyOf）。

分子分母都只在 `type=core` 的子集里求和，plus 不出现在这两个求和号里的任何一处。

`min(L, T)` 是关键：超出要求的能力不额外加分。否则学生只要有一段实习经历就能把分数拉满，诊断失去意义。

### 6.3 为什么不做 core 归一化

三岗 core 权重分别是 79 / 89 / 83，加起来不是 100。有人会想「先把 core 放大到 100 再算」。

不这么做，理由不是数学（等比缩放后 `M_core` 数值不变，因为分子分母同比放大），而是**可读性**：面板上如果显示「JavaScript 权重 11.4」，而模型里它是 9，学生就会对不上账。保持原值，`M_core` 一样正确。

### 6.4 技能缺口与补强优先级

```
gap_i      = max( T_i − L_i, 0 )        // 只对 core
priority_i = w_i × gap_i                // 只对 core，降序
Top3       = priority 前三（并列时按 w 降序、再按 skillId 字典序稳定排序）
```

plus 不进入这个排序。一个 plus 项差距再大，也不会出现在「优先补强」里——它只出现在「额外优势 · 待补」清单中。

### 6.5 plus 的输出结构

plus 不进百分比，但必须**可见**，否则加分项等于从产品里消失。输出结构固定为：

```
plusSkills = {
  mastered: [ { skillId, name, dim, current, target, weight } ],   // L ≥ T
  pending:  [ { skillId, name, dim, current, target, weight, gap } ], // L < T
  summary:  { masteredCount, pendingCount, totalCount }
}
```

界面规则：

- 标题写「额外优势」，不写「加分项得分」。
- 只输出**计数**，例如「已掌握 3 / 7 项加分技能」。**不得**换算成百分比、不得与 `M_core` 相加、不得做「综合竞争力指数」之类的合成分。
- 每项必须显示当前等级与目标等级两列，否则「已掌握」没有依据。

### 6.6 anyOf

前端岗 `vue` 要求带 `anyOf: ["react"]`，规则：

```
L_eff(req) = max( L(req.skillId), L(req.anyOf[0]), L(req.anyOf[1]), ... )
```

- **匹配度只计一次**：分子加 `w × min(L_eff, T)`，分母加 `w × T`，各一次。
- **差距分析也只出一条**：`gap = max(T − L_eff, 0)`，`priority = w × gap`。绝不允许 vue 和 react 各出一条缺口——那等于同一项要求被算了两次。
- **成员不得是独立 requirement**：`react` 不在前端岗的 `requirements` 里，只在 `anyOf` 中。校验器会拒绝「anyOf 成员同时被写成独立 requirement」的数据。
- **成员不进维度画像**：维度画像按 owning requirement 聚合，react 的等级只会通过 vue 那条要求体现，不会在「岗位技术栈」轴上被单独计一次。
- 成员不在词典中 → 忽略该成员，按剩余项取最大值。

### 6.7 雷达图口径与空轴

```
T_dim = Σ_core( w × T ) / Σ_core( w )       // 目标线，只用 core
L_dim = Σ_core( w × L_eff ) / Σ_core( w )   // 当前线，同权重同口径
```

当前线和目标线必须用**同一组 core 权重**，否则两条线不可比（这是最容易写错的地方：当前线若按个人评过的所有技能算，plus 会偷偷抬高当前线，等于变相加分）。

**空维处理（不能除以零）**：某维度没有 core 要求时，`Σ_core(w) = 0`，返回 `null` 而不是 0。

| 岗位 | 空 core 维度 | 有效数据轴 |
|---|---|---|
| 前端开发 | 数据与存储、分析与洞察 | **4 条** |
| Java 后端 | 分析与洞察 | **5 条** |
| 数据分析 | 无 | **6 条** |

绘制规则：**六条轴恒定存在**（产品视觉与维度认知不随岗位变），空轴保留轴线与标签，标注「无核心要求」，不画数据点，折线在相邻有效轴之间直连。**不得用 0 代替 `null`**——0 会被读成「该维度要求为零，随便怎样都行」，而真实含义是「本岗位不把它当核心要求」。

这是 core-only 规则最直接的可视化后果：前端雷达图只有 4 个数据顶点。我认为这是诚实的，但它是产品观感上的显著变化，列在第十节请你确认。

### 6.8 边界与脏数据处理

| 输入情况 | 处理 | 结果 |
|---|---|---|
| 未做任何自评 / 空对象 | 所有 `L` 视为 0 | `M_core = 0`；界面显示「尚未完成自评」，不把 0% 当真实水平 |
| 全部自评为 0 | 正常计算 | `0%`，是有效结果；Top3 等价于「按权重从高到低补」 |
| 某维度无 core | 返回 `null` | 不参与计算，不做除法，无除零/Infinity |
| `Σ_core(w×T) = 0` | 返回 `null` + `NO_CORE_REQUIREMENT` | 界面显示「该岗位暂无核心要求」，禁止 0%/NaN |
| 未知 skillId | 构建期失败；运行期跳过并 warn | 不计入分子分母，其余项不受影响 |
| 同岗 skillId 重复 | 构建期失败；运行期按首条去重 | 权重不会翻倍 |
| anyOf 成员被写成独立 requirement | 构建期失败；运行期忽略独立那条 | 同一技能不会被计两次 |
| 自评越界 / 小数 / 非数字 | 非数字→0，小数四舍五入，夹取到 [0,5] | `[-3,9,3.5,2.4,"abc",null,true]` → `[0,5,4,2,0,0,0]` |
| 自评含本岗未要求的技能 | 保留在画像，不进分子分母 | 唯一例外：它是本岗某条要求的 anyOf 成员 |
| 岗位权重合计 ≠ 100 | 构建期失败；运行期直接报错 | 不自动归一化，避免输出「看似正常的错误百分比」 |

### 6.9 P2 实现骨架

```js
const clamp = v => Math.max(0, Math.min(5, Math.round(Number(v) || 0)));

const effLevel = (req, lv) =>
  (req.anyOf || []).reduce((m, id) => Math.max(m, clamp(lv[id])), clamp(lv[req.skillId]));

function matchCore(job, lv) {
  let num = 0, den = 0;
  for (const r of job.requirements) {
    if (r.type !== 'core' || r.target <= 0) continue;
    num += r.weight * Math.min(effLevel(r, lv), r.target);
    den += r.weight * r.target;
  }
  return den === 0 ? { value: null, reason: 'NO_CORE_REQUIREMENT' }
                   : { value: num / den * 100, reason: null };
}

function dimProfile(job, lv) {           // 六维，空维为 null
  return Object.fromEntries(dims.map(d => {
    const rs = job.requirements.filter(r =>
      r.type === 'core' && dimOf(r.skillId) === d.id && r.target > 0);
    if (!rs.length) return [d.id, null];
    const w = rs.reduce((a, r) => a + r.weight, 0);
    return [d.id, {
      target:  rs.reduce((a, r) => a + r.weight * r.target, 0) / w,
      current: rs.reduce((a, r) => a + r.weight * effLevel(r, lv), 0) / w
    }];
  }));
}
```

`plus` 的拆分是一个独立函数，**不允许**在 `matchCore` 里出现任何 plus 分支——物理隔离比注释可靠。

## 七、计算测试案例

全部用真实数据跑出，不是手算示例。

### 7.1 缺失 plus 不会降低基础匹配度（前端岗）

`Σ_core(w×T) = 255`。

| 场景 | M_core | 已掌握 plus | 待补 plus |
|---|---|---|---|
| core 全达标 / plus 全 0 | **100.00%** | 0 | 10 |
| core 全达标 / plus 全 5 | **100.00%** | 10 | 0 |
| core 全 0 / plus 全 0 | **0.00%** | 0 | 10 |
| core 全 0 / plus 全 5 | **0.00%** | 10 | 0 |
| core 打半 / plus 全 0 | **41.18%** | 0 | 10 |
| core 打半 / plus 全 5 | **41.18%** | 10 | 0 |

三组对照说明三件事：

1. 1、2 行：plus 从 0 到 5，`M_core` 一模一样 → **已掌握 plus 不加分**。
2. 3、4 行：plus 全满，`M_core` 仍是 0 → **plus 不能把分数拉起来**，它不在分子里。
3. 5、6 行：plus 从 0 到 5，`M_core` 一模一样 → **未掌握 plus 不扣分**，它不在分母里。

同结构两名学生的精确对比：甲（plus 全 0）`41.1765%`，乙（plus 全 5）`41.1765%`，差值 `0.0000000000`。

第 5 行也是「诊断有效」的证据：core 打半就是 41.18%，不会因为 plus 拉满而虚高。

### 7.2 anyOf 只计一次（前端 vue ↔ react，w=9，T=4）

固定其余 core 全部达标，只改这两项。

| vue | react | 有效等级 | 该项得分 `w×min` | 占该项满分 | M_core |
|---|---|---|---|---|---|
| 0 | 0 | 0 | 0 | 0.0% | 85.88% |
| 0 | 4 | 4 | 36 | 100.0% | **100.00%** |
| 1 | 4 | 4 | 36 | 100.0% | 100.00% |
| 2 | 2 | 2 | 18 | 50.0% | 92.94% |
| 3 | 0 | 3 | 27 | 75.0% | 96.47% |
| 4 | 0 | 4 | 36 | 100.0% | 100.00% |
| 6 | −1 | 5→夹取4 | 36 | 100.0% | 100.00% |

证明三点：

1. **只计一次**：分母含 vue 一次为 255，去掉 vue 后为 219，差值 36 = 9×4。`react` 从未在分母里单独出现。
2. **取最高**：vue=1、react=4 得满分；vue=3、react=0 得 75%。学 React 的学生不会因为没有 Vue 而丢掉那 9 分。
3. **不重复**：`react` 不是前端岗的独立 requirement，`gap` 也只产出一条（vue 那条）。

### 7.3 缺口与优先级（前端 / core 全 0）

| 排名 | 技能 | w | T | L | gap | priority |
|---|---|---|---|---|---|---|
| 1 | JavaScript 核心语法 | 9 | 4 | 0 | 4 | 36 |
| 2 | Vue 框架 | 9 | 4 | 0 | 4 | 36 |
| 3 | HTML 与 CSS 布局 | 8 | 4 | 0 | 4 | 32 |
| 4 | TypeScript 类型系统 | 5 | 3 | 0 | 3 | 15 |
| 5 | 浏览器工作原理 | 4 | 3 | 0 | 3 | 12 |

即使把 plus 全部拉到 5 级，Top3 依然是这三项——plus 不进排序。

### 7.4 边界

| 输入 | 输出 |
|---|---|
| 空自评对象 `{}` | `0.0`（界面另显示「尚未完成自评」） |
| core 全 0 | `0.0` |
| 只有一条 core 且 target=0 | `null` + `NO_CORE_REQUIREMENT` |
| 只有 plus，没有 core | `null` + `NO_CORE_REQUIREMENT` |
| 混入未知 skillId | 跳过该条，其余正常（`100.0`） |
| 同一 skillId 重复两次，L=2/T=4 | 按首条去重，`50.0`（不是 100，也不是 25） |
| 越界/小数/非数字 | `[-3,9,3.5,2.4,"abc",null,true]` → `[0,5,4,2,0,0,0]` |

## 十、已知局限（请在验收时一并确认）

1. **前端雷达图只有 4 个数据顶点。** 数据与存储、分析与洞察两维在前端岗没有 core，按 6.7 的规则这两轴不画数据点。三岗轴数因此是 4/5/6。
   - 我的判断：这是诚实的，因为前端岗确实不把数据分析当核心要求；用 0 代替 `null` 反而会被读成「这维度不重要」。
   - 代价：三岗雷达图形状不可直接横比（但本产品一次只看一个岗位，且权重体系本就不同，横比本来也不成立）。
   - 如果你更看重「六边形」的统一观感，可选方案是把空轴的目标画成 0——但那样当前线会在该轴凸出，视觉上像「巨大优势」，而它在百分比里一分不加，图文不一致。**这条请你定。**
2. **数据分析师「编程基础」由单一技能决定。** 该维 core 只剩 Python（w9/T4），画像 4.00 完全由它决定，结果分析师在这一轴反而高于前端（3.57）和 Java（3.59）。这是分类口径造成的错觉，不是真实差异（ds-algo、regex、oop-design 都划成了 plus）。
   - 代价最小的修法：把 `ds-algo` 在分析岗升为 core。但这会把 core 权重从 83 改成 87，破坏你确定的 83，**所以我没动**。
   - 另一种修法：接受现状，在 UI 上对单技能维度加弱化标注。**这条也请你定。**
3. **权重是示例值。** 没有真实 JD 抽样，所有权重属于「看起来合理」而非「统计得出」。这是本方案最大的风险，也是 `calibration` 字段存在的理由。
4. **61 项低于 60–80 区间的中位。** 这是「每项必须被引用」原则的结果——原始 73 项有 12 项是死重。若要保留更大词表，可恢复并加 `coverage: "reserved"`，代价是自评页变长。
5. **数据分析岗没有「完整项目交付经验」。** 校招分析岗确实较少强制要求。若认为该有，建议给 2 分并从 Python 的 9 分里出。
6. **core / plus 的划分本身也是示例判断。** 它比权重更影响结果：把一项从 core 挪到 plus，等于把它从「必须」降为「有没有都行」。后续用真实 JD 校准时，这一步要和权重一起校准，不能只调数字不改分类。

## 十一、数据结构说明

### skills.json（未改动）

```
meta       版本、免责声明、别名解析规则、等级说明
dimensions 6 个维度：id / name / short / desc / why
```

### jobs.json（r2 新增字段）

```
meta
  version / revision / revisionNote   数据版本 v0.1，修订号 r2
  displayBadge                        「示例数据 v0.1」，界面直接取用
  disclaimer / seniority              免责声明与岗位层级
  scoring
    version / changeNote              v0.2-core-only 及变更说明
    formula / formulaNote             M_core 公式与分母口径
    typeNote                          core / plus 的职责边界
    weightPolicy                      100 = core + plus；不归一化；plus 不计分
    levelRule / statusRule / gapRule  等级夹取、三态、缺口与优先级
    anyOf                             rule / countOnce / gapOnce / missingMember / keep
    radar                             target / current / plus / emptyDim / axes / note
    edgeCases[]                       10 条边界规则（case / handling）
  calibration                         校准状态、预留字段、type 调整须同步文档
  coverageRule                        61 项全部被引用；anyOf 成员视为被引用但不单独计权
jobs[]
  id / name / shortName / seniority / summary / notes
  scoringScope                        「基础匹配度仅取 core」的显式声明
  └ requirements[]  skillId / weight / target / type / anyOf? / anyOfNote?
```

### 计分口径速查（P2 实现依据）

```
M_core  : Σ_core(w×min(L_eff, T)) / Σ_core(w×T) × 100%
L_eff   : max(自身, anyOf 成员…)，夹取 [0,5]
状态    : 缺失 L=0；薄弱 0<L<T；已掌握 L≥T（仅 core）
gap     : max(T − L_eff, 0)（仅 core）
priority: w × gap（仅 core），降序取 Top 3
T_dim   : Σ_core(w×T) / Σ_core(w)；空维 null
L_dim   : Σ_core(w×L_eff) / Σ_core(w)；与 T_dim 同权重
plus    : 只出 mastered / pending 两个清单 + 计数，不进任何百分比
```

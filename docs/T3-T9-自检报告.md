## 1. T3 · 技能图谱与 JD 解析

**交付物**：`SkillController`（3 个查询）、`JobController` + `JobService`（岗位 CRUD、解析、要求覆盖）、
`/jobs` 页（列表 + 录入 + 解析草稿表格 + 保存）、`/skills` 页（6 维分组 + 搜索 + 关系抽屉 + 我的等级）。

| 契约 | 实测 |
|---|---|
| `GET /api/skills/categories` | 200，6 条，含 `short`（用 `@JsonProperty` 把 `shortName` 映射回契约名） |
| `GET /api/skills?categoryId=foundation` | 200，前缀返回 `js-core…` |
| `GET /api/skills/relations` | 200，**41 条**（原为空表，见 1.2） |
| `POST /api/jobs` | 201，`parseStatus=pending` |
| `POST /api/jobs/{id}/parse` | 200，示例 JD 解析出 **9 项**（全部 required），含 `matchedAlias / sourceStart / sourceEnd / evidenceHint` |
| `PUT /api/jobs/{id}/requirements` | 200，覆盖写，返回 6 条；`parseStatus` 变 `confirmed` |
| 重复/未知技能 | 409 `DUPLICATE_RESOURCE` / 422 `UNKNOWN_SKILL`（Java 测试 `JobControllerTest` 覆盖） |
| 越权 | 他人岗位 `JOB_NOT_FOUND` 404（含 DELETE） |

> 示例 JD 的 9 项全部被判为「必备」，**加分分类没有被这段 JD 触发**——这是数据巧合，不是功能缺失：
> 分句判定加分的用例在 pytest `tests/test_jd_parser.py::test_required_and_bonus_are_split_by_clause`
> （`redis` 在该用例里被判 `bonus`）。T3-R 若要验收加分链路，建议用带「加分项：有…者优先」的 JD 复验。

### 1.1 两条实现口径（请裁定）

1. **解析不落库**：`POST /{id}/parse` 只调 Python 并把建议原样返回，**不改 `parse_status`、不写要求表**；
   用户点保存后才写并要求置 `confirmed`。这样「误点解析」不会污染要求表。
2. **要求保存是整体覆盖**，不是合并：接口层没有「删除单条」的动作，合并语义会让「删掉一条误识别」不可能。
   覆盖前先整批校验（技能存在、类型枚举、权重 1–99、目标 1–5、`anyOf` 成员存在），任一条非法整批拒绝。

### 1.2 修掉的一处「空表」

`skill_relation` 在 T0 建表后**一直是空的**（`data/skills.json` 没有关系字段），这违反 c3.3
「一期不得预留空表」。本轮补 `data/skill-relations.json`（41 条：prerequisite / related / ecosystem），
`SkillSeedRunner` 幂等导入（`INSERT IGNORE` + 导入前校验两端技能存在，坏数据跳过并告警，
不借用外键报错来兜底）。Python 侧不读这个文件——它只需要技能清单。

### 2.1 空值语义的三次实测（另一轮独立实测，与第 3 节的脚本不是同一次）

```
第一次（未自评）：status=EMPTY_PROFILE  requiredScore=null  bonusScore=null
                 numerator=0  denominator=13  counts.requiredMissing=6
第二次（只完成一个任务、等级 4）：status=ok  requiredScore=23.0769  numerator=3  denominator=13
证据覆盖：evidenceCoverage=33.33（2/6），全程未参与 requiredScore 计算
```

**需要裁定的一处**：`EMPTY_PROFILE` 时 `requiredScore` 为 `null`（符合契约），但 `numerator/denominator`
仍返回 `0 / 13`。这两个数是「如果做了自评，分母会长这样」的信息，不是分数；但页面上若同时显示
「null%」和「0 / 13」容易被读成矛盾。**当前处理**：前端在 `requiredScore == null` 时只显示「—」，
不展示分子分母。是否要求后端在 `EMPTY_PROFILE` 时把分子分母也置 null，请裁定。

### 2.2 快照与算分

- 每次 `POST /api/match` 与 `POST /api/reports` 都会**新增一条快照**（不覆盖）。`algorithm_version`
  取 Python 返回的 `meta.scoringVersion`。
- `skill_gap_report` 与结果 1:1，存 `gap_items` / `top_priorities` / `explanation`（含 counts/meta/bonusItems）。
- Python 返回体用 `Map` 接收而不是逐字段 record：快照要**原样存档**，record 会丢掉未来新增的字段。
- 异常映射：连接失败/超时/5xx → 503 `ANALYSIS_UNAVAILABLE`；响应缺 `status/counts/radar` → 502 `ANALYSIS_FAILED`。

### 2.3 雷达图

`SkillRadar.vue` 手写 SVG（不引图表库）。某维度 `target == null` 时：**不画点、不连线**，
轴线变虚线并标注「不要求」；只要有一个空轴，整体不画多边形，只画有值的点，并附一行说明。
这是契约「不画点、不连到 0」的直接实现。

## 3. T5 · 学习路径闭环

**交付物**：`TaskController` + `TaskService`、`/tasks` 页（过滤、开始/搁置/完成、新建）。

| 契约 | 实测 |
|---|---|
| `POST /api/tasks/from-gap/{jobId}` | 201，`{"created":2,...}`，标题形如「补齐「MySQL 事务与锁」：L0 → L2」 |
| 去重 | 同技能已有 todo/doing 任务时跳过（Java 测试覆盖过滤与状态机） |
| `PATCH /api/tasks/{id}` | 200；置 `done` 写 `completedAt`，改回 `todo` 清空 |
| `POST /api/tasks/{id}/complete` | 200，`status=done`、`recalculated=true`、`matchedJobId=<jobId>`，快照分数由 **66.6667 → 83.3333**（把该技能自评从 L1 提到 L3 后重算） |

**重算口径（请重点看）**：完成任务并更新等级后，取「最近一个要求了该技能的岗位」重算。
理由：用户是从那个岗位的匹配页过来的，心智对得上；若要重算全部岗位，一次完成动作会触发 N 次
Python 调用并写 N 条快照，反而污染趋势。没有岗位引用该技能时 `recalculated=false`、
`matchedJobId` 缺省——它表示「真的重算过」，不是「大概可以重算」。
重算失败（分析服务没起）**不回滚完成动作**：任务做完是事实，前端提示「稍后重新匹配」。

## 6. T8 · 面试复盘（二期模块 8 简化版）

**新增表** `interview_record`。**与看板原描述的偏差（如实说明）**：看板写的是「一条记录可挂岗位与多问题；
薄弱点标签可存可查」，本轮**没有做独立的「薄弱点标签」**，改为：
`questions[{question,selfRating,note}]` + `relatedSkills[]`（关联到技能词典里的真实技能）。
理由：薄弱点在数据上就是「被追问且自评低的技能」，再引入一套标签体系会与技能词典重复；
`relatedSkills` 还能直接回指到画像与匹配。若评审要求独立标签，需再加一张关联表，请在 T8-R 裁定。

| 契约 | 实测 |
|---|---|
| `POST /api/interviews`（带 applicationId） | 201，`companyName/jobTitle` 从投递记录带出，`result=pending` |
| `questions[]` | 空行自动忽略，`selfRating` clamp 到 1–5，单场最多 30 条 |
| `PATCH /{id}` | 200，可改 `result`（pending/pass/reject）、复盘正文、题目 |
| `GET /api/interviews` | 200，按面试日期倒序 |

## 7. T9 · 数据看板（不单开页面）

`GET /api/stats/insights` 实测：

```json
{"applicationStatus":[{"status":"applied","count":1}],
 "interviewResult":[{"status":"pending","count":1}],
 "matchTrend":[3 条，含 requiredScore:23.0769 / 23.0769 / null],
 "topGaps":[{"skillId":"db-mysql","skillName":"MySQL 事务与锁","count":1,"priority":2}],
 "taskCompletion":{"done":1,"total":2,"rate":50.0}}
```

三块聚合都只用已有表，不新增埋点表。`topGaps` 只统计**每个岗位最近一次**快照：
把历史快照全算进来会让「反复匹配同一岗位」把频次刷高。`taskCompletion.rate` 在无任务时为 `null`（不适用），
不是 0%。

> 本文件是 Trae 与 WorkBuddy 两个 AI 协作的**唯一事实源**。双方每次开工先读本文档，收工前更新第四节任务看板。
> 版本 c2.1 · 2026-11-15 · 与 AGENTS.md v2.0 配套
> **c2.0 变更**：WorkBuddy 改为全栈实现方，Trae 改为评审方；分支由 `backend`/`frontend` 两人各一，改为 `dev` 开发 + 评审合 `main`。
> **c2.1 变更**：修复示例数据里的 3 个假技能 id；`gaps` 只收 `gap>0`；3.3 补全局免责声明入口；3.5 补 `numerator`/`denominator` 与 `radar.axes[].coreWeight`；表数更正为 9 张。详见第四节变更记录。

## 一、角色与边界

| 角色 | 负责范围 | 禁止越界 |
|---|---|---|
| **WorkBuddy（全栈实现）** | `backend/` 全部代码、MySQL 建表与 seed、匹配算分与 pytest、`frontend/` 全部页面与样式 | 不改 `data/*.json`、不改第三节接口契约字段 |
| **Trae（评审方）** | 读代码、跑测试与接口、按第六节清单出问题清单、维护 `docs/评审记录.md`、评审通过后合入 `main` | **不写业务代码**，不直接改 WorkBuddy 的文件；发现问题只提清单，由 WorkBuddy 修 |
| **项目负责人（用户）** | 阶段裁决、提供数据库连接信息、验收 | — |

**接口契约冻结**：第三节的字段名、类型、枚举值任何一方都不得单方面修改。确需变更时，先在本文档改契约并升版本号（c2.0 → c2.1），在第四节记一条「契约变更」，经用户与评审方确认后再改代码。

## 二、Git 工作流

| 分支 | 用途 | 说明 |
|---|---|---|
| `main` | 已验收基线 | **只有 Trae 评审通过后才能合入**；任何时刻必须可运行 |
| `dev` | WorkBuddy 开发 | 全部开发提交在此；评审不通过原地修，不新建分支 |

**WorkBuddy 开工前**：

```powershell
git status          # 必须干净
git switch dev
```

**WorkBuddy 收工前**：`git add` 具体文件 → `git commit`。提交信息前缀：`feat:` / `fix:` / `test:` / `style:` / `docs:` / `chore:`，示例 `feat: 岗位只读接口与 seed 脚本`。

**Trae 评审流程**：

```powershell
git switch dev
git log main..dev --oneline     # 看这一轮交付了哪些提交
git diff main...dev --stat      # 看改动范围
# 跑测试 / 启服务验证，结论写入 docs/评审记录.md
git switch main && git merge --ff-only dev   # 仅在全部阻断项修复后
git switch dev && git merge --ff-only main   # 保持 dev 不落后
```

**铁律**：
- `main` 出现未评审代码 = 流程违规，必须回滚。
- 阻塞项（P0）未清零不得合入；建议项（P1）可留到下阶段。
- 谁合并谁负责跑通一遍启动命令，不接受「代码看起来没问题」。
- 禁止 `git checkout --`、`git reset --hard` 覆盖对方成果。

## 三、接口契约（冻结 c2.1）

### 3.1 通用约定

| 项 | 约定 |
|---|---|
| 基础地址 | 后端 `http://127.0.0.1:8000`；前端开发经 Vite proxy，统一请求 `/api/...` |
| 字段命名 | **JSON 一律 camelCase**（后端 Pydantic alias 转换，禁止返回 snake_case） |
| 鉴权 | `Authorization: Bearer <accessToken>`；免鉴权白名单：`/api/auth/register`、`/api/auth/login`、`/api/skills*`、`/api/jobs*`、`/docs` |
| 时间 | ISO 8601 字符串，UTC 带 `Z`，如 `2026-11-15T08:30:00Z` |
| 成功响应 | 直接返回资源对象或 `{items: [...]}`，**不包一层 code/data** |
| 错误响应 | HTTP 4xx/5xx + `{"detail": {"code": "USERNAME_TAKEN", "message": "用户名已存在"}}` |
| 分页 | 第一版不分页，列表全量返回 |

### 3.2 认证

**POST `/api/auth/register`**

```json
// 请求
{ "username": "student01", "password": "123456" }
// 201
{
  "accessToken": "eyJhbGciOi...",
  "tokenType": "bearer",
  "user": { "id": 1, "username": "student01", "role": "student", "createdAt": "2026-11-15T08:30:00Z" }
}
```

错误：`409 USERNAME_TAKEN`、`422 VALIDATION_ERROR`（用户名 3–32 位字母数字下划线，密码 6–64 位）。

**POST `/api/auth/login`** 请求同上，`200` 响应同 register；错误 `401 INVALID_CREDENTIALS`。

**GET `/api/auth/me`** → `{ "id": 1, "username": "student01", "role": "student", "createdAt": "..." }`；未登录 `401 UNAUTHORIZED`。

### 3.4 技能画像（需鉴权，只能操作本人数据）

**Profile 对象**

```json
{
  "id": 7, "name": "我的求职画像",
  "createdAt": "2026-11-15T08:30:00Z", "updatedAt": "2026-11-15T08:35:00Z",
  "skills": [ { "skillId": "js-core", "name": "JavaScript 核心语法", "dim": "foundation", "level": 3 } ]
}
```

| 方法 | 路径 | 请求 | 响应 |
|---|---|---|---|
| POST | `/api/profiles` | `{ "name": "我的求职画像" }` | `201` Profile（`skills` 为空数组） |
| GET | `/api/profiles` | — | `{ "profiles": [ { "id": 7, "name": "…", "updatedAt": "…", "skillCount": 12 } ] }` |
| GET | `/api/profiles/{id}` | — | Profile |
| PUT | `/api/profiles/{id}` | `{ "name": "可选", "skills": [ {"skillId":"js-core","level":3} ] }` | Profile |
| DELETE | `/api/profiles/{id}` | — | `204` 无响应体 |

规则：`PUT` 的 `skills` 为**全量覆盖**（先删后插）；`level` 取整并 clamp 到 `[0,5]`，缺省按 0；未知 `skillId` 返回 `422 UNKNOWN_SKILL`；他人画像返回 `404 PROFILE_NOT_FOUND`（不暴露存在性）。画像数量上限 10 份，超出 `409 PROFILE_LIMIT`。

### 3.5 匹配与差距分析（需鉴权）

**POST `/api/analysis/match`**

```json
// 请求
{ "profileId": 7, "jobId": "frontend" }
```

`profileId` 可为 `null`，此时必须同时传 `skills` 做试算（不落库）：

```json
{ "profileId": null, "jobId": "frontend", "skills": [ { "skillId": "js-core", "level": 3 } ] }
```

**响应 MatchResult**

```json
{
  "jobId": "frontend", "jobName": "前端开发工程师",
  "profileId": 7,
  "matchScore": 41.1765,
  "status": "ok",
  "numerator": 105,
  "denominator": 255,
  "counts": { "mastered": 6, "weak": 8, "missing": 5, "plusMastered": 3, "plusPending": 8 },
  "gaps": [
    {
      "skillId": "ts-type", "skillName": "TypeScript 类型系统", "dim": "stack",
      "weight": 7, "target": 3, "level": 1, "effectiveLevel": 1,
      "gap": 2, "priority": 14, "status": "weak"
    }
  ],
  "topActions": ["ts-type", "unit-test", "vue"],
  "plusItems": [ { "skillId": "frontend-build", "skillName": "构建工具", "dim": "engineering", "weight": 3, "target": 2, "level": 2, "status": "mastered" } ],
  "radar": {
    "axes": [
      { "dim": "foundation", "name": "编程基础", "target": 3.82, "current": 3.1, "hasCore": true, "coreWeight": 30 },
      { "dim": "data", "name": "数据与存储", "target": null, "current": null, "hasCore": false, "coreWeight": 0 }
    ],
    "dataAxisCount": 4
  },
  "meta": { "scoringVersion": "v0.2-core-only", "displayBadge": "示例数据 v0.1", "disclaimer": "…" }
}
```

> c2.1 修的两个问题：
> 1. 示例里的 `ts` / `engineering-test` / `webpack` **不是词典里的 id**（实际是 `ts-type` / `unit-test` / `frontend-build`），
>    照抄会直接 `422 UNKNOWN_SKILL`。这不是笔误——词典里压根没有叫 `ts` 的技能。
> 2. `numerator` / `denominator` 是新增字段。原契约只给 `matchScore`，评审要验「分母是 255 不是 100」
>    得自己把 19 条要求的权重一个个乘回去。直接暴露组成项，这条硬规则就能一眼核对。

字段与口径（**与 AGENTS.md 第八节完全一致，不得改**）：

| 字段 | 规则 |
|---|---|
| `matchScore` | `M_core = Σ_core(w×min(L,T)) / Σ_core(w×T) × 100`，保留 4 位小数；无 core 或分母为 0 时返回 `null`，配 `status = "NO_CORE_REQUIREMENT"` |
| `status` | `ok` \| `NO_CORE_REQUIREMENT` \| `EMPTY_PROFILE`（未做任何自评，`matchScore` 返回 `null`，界面提示「尚未完成自评」，不得显示 0%） |
| `counts` | `mastered / weak / missing` 仅统计 core；`plusMastered / plusPending` 仅统计 plus |
| `gaps` | 仅 core 且 `gap > 0`，按 `priority = w × gap` 降序；`status` 只有 `missing`（L_eff=0）与 `weak`（0<L_eff<T）两态。已掌握的技能不进本列表——它不是「差距」（c2.1 澄清） |
| `effectiveLevel` | `anyOf` 命中时 `L_eff = max(自身, 成员)`；该要求只出一条记录，成员不得独立出现。同时返回 `level`（自身）与 `effectiveLevel`（含成员），用来区分「Vue 本身达标」与「React 代为达标」 |
| `topActions` | 取 `gaps` 前 3 个 `skillId`，不足 3 个按实际数量 |
| `plusItems` | `status` 只有 `mastered` / `pending` 两态，不参与任何百分比；元素含 `dim`（c2.1），便于前端按维度分组展示 |
| `radar.axes` | 恒定 6 条；`T_dim = Σ_core(w×T)/Σ_core(w)`，`L_dim = Σ_core(w×L_eff)/Σ_core(w)`；无 core 维 `target/current` 均为 `null`、`hasCore=false`、`coreWeight=0`；**禁止用 0 代替**。`coreWeight` 为维度内 core 权重和（c2.1），前端可标注「该维度占 30 分」 |
| `dataAxisCount` | `hasCore=true` 的轴数量，实测前端 4 / Java 5 / 分析 6 |

错误：`404 JOB_NOT_FOUND`、`404 PROFILE_NOT_FOUND`、`422 UNKNOWN_SKILL`。

### 3.7 简历文本解析（P5 交付，先占位）

**POST `/api/resume/parse`**：`{ "text": "…粘贴的简历文本…" }` →
`{ "suggestions": [ { "skillId": "js-core", "name": "JavaScript 核心语法", "dim": "foundation", "level": 2, "matchedAlias": "javascript", "evidence": "…原文片段…" } ] }`

**硬规则**：返回值只是预填建议，前端必须允许逐条修改后再保存画像；不得自动写库。解析必须按「英文别名长度倒序 + 词边界、中文别名子串」执行，并遮蔽已匹配区间，防止 `js⊂next.js`、`spring⊂spring cloud`。

## 五、联调与验收

**启动命令**

```powershell
# 后端（在项目根）
cd backend
py -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

> 注意：本机 `python.exe` 指向 WindowsApps 坏存根，`python` 命令会报错，**必须用 `py`**。

**交付定义（WorkBuddy 提评审的前置条件）**：代码已提交到 `dev`；接口用 `/docs` 或 `curl` 实测过并附请求/响应；页面能 `npm run dev` 打开并完成一次真实请求；看板状态改为 🟡。

**验收定义（Trae 评审通过的标准）**：第六节清单内 P0 项全部为零；我亲自跑一遍启动命令与关键接口；结论写入 `docs/评审记录.md`。

**验收顺序**：P1-1 → P1-2 → P1-3 → R1 → P2 → R2 → P3 → R3 → P4 → R4 → P5 → R5。

**禁止事项**：改契约不通知、跳过评审直接合 `main`、把 plus 算进匹配度、空轴画 0、把示例权重说成企业标准、把 `.env` 提交入库。

## 六、评审规范（Trae 执行）

### 6.1 问题分级

| 级别 | 含义 | 处理 |
|---|---|---|
| **P0 阻断** | 口径错、越权、数据错、跑不起来 | 必须修复，复核通过才可合 `main` |
| **P1 建议** | 不影响正确性，涉及可维护性/体验 | 可留到下阶段，但需记入待办 |
| **P2 提示** | 风格、命名、注释 | 不阻塞 |

### 6.2 检查清单

**A. 契约一致性（每轮必查）**
- [ ] 返回字段全 camelCase，无 snake_case 泄漏
- [ ] 错误体为 `{"detail":{"code","message"}}`，错误码与看板一致
- [ ] `anyOf` 恒为数组，无成员时 `[]` 而非 `null`
- [ ] 时间格式 `...Z`；`404` 与 `401` 语义正确

**B. 计分正确性（R3 重点）**
- [ ] `M_core` 只在 core 内求和，分母是 `Σ_core(w×T)` 而非 100
- [ ] plus 完全不进分子分母，`plusItems` 只有 `mastered/pending`

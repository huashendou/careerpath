**空档案为什么是 9 个 `null` 而不是 8 个**：8 个可写字段全 `null`，外加 `updatedAt` 也是 `null`
（从未保存过）。这是有意的——用 `updatedAt: null` 区分「从没填过」和「填过又清空」，前端据此
显示「尚未填写」而不是某个保存时间。评审时若把这 9 个当一致性问题，请对照本节结论。

**全新账号的空态原文**（另起账号单独取，未经任何写入）：

```
--- /api/profile ---
{"realName":null,"school":null,"major":null,"grade":null,"targetJobType":null,
 "targetCity":null,"phone":null,"email":null,"updatedAt":null}
--- /api/stats/overview ---
{"profileCompleted":false,"jobCount":0,"taskOpenCount":0,"evidenceMissingCount":0,
 "lastMatch":null,"generatedAt":"2026-11-15T12:41:40.811599600Z"}
```

**`profileCompleted` 的判定口径（本轮改过）**：`school` 与 `major` 均非空（`TRIM` 后判空）才算
完善，其余六个字段不参与。四种状态实测：

```
1 空档案            -> "profileCompleted":false
2 只填手机号与邮箱  -> "profileCompleted":false   ← 旧口径这里是 true
3 学校+专业         -> "profileCompleted":true
4 学校改成全空格    -> "profileCompleted":false
```

选这个口径的理由：概览页那格写的是「已完善 / 学校专业已记录」，判据得和文案对得上；而
「有 `user_profile` 行」既不能证明填过东西，也会被一次空的 PUT 触发。

## 3. C 组 · 数据与 SQL

- `user` 表：`username` 唯一索引、`password_hash`、`role` 默认 `'student'`、`created_at`/`updated_at`。
- `user_profile.user_id` 唯一且 `ON DELETE CASCADE` → 一个账号最多一份档案，删号即删档案。
- **`role` 默认值这轮改过**：T0 的 `schema.sql` 写的是 `'STUDENT'`，而契约样例与
  `AuthResponse.user.role` 都是小写 `student`。不统一会出现「同一账号，注册响应 `student`、
  库里 `STUDENT`」的漂移。已同步改文件与库内表定义（`ALTER TABLE`），因此本轮的接口实测
  是在**已生效的库**上跑的，不是只在文件里对齐。
- 种子数据未被本轮触碰：实测结束再核一次，`skill` 61 行、`skill_category` 6 行，与 T0 一致。

## 4. D 组 · 安全

| 检查点 | 结论 |
|---|---|
| 无令牌访问 `/api/profile`、`/api/stats/overview` | 均 401（第 2 节第 11 项 + `StatsControllerTest` 用例） |
| 错误密码 | 401，错误体 `{"detail":{"code","message"}}`，不区分「用户不存在」与「密码错误」 |
| 密码存储 | BCrypt(10)，`password_hash` 不出现在任何响应体（`AuthResponse` 只回 id/username/role/createdAt） |
| 越权隔离 | `ProfileController` 两个方法都只从 `@AuthenticationPrincipal` 取 `id`，**不接收路径参数或请求体里的用户 id**，因此不存在改 id 读别人档案的入口；`requirePrincipal` 对 null 直接抛 401 |
| 令牌失效 | 伪造令牌访问 `/profile`：守卫调 `/auth/me` 得 401 → 清 `localStorage` → 跳登录页（第 5 节实测） |
| JWT 密钥 | 无 `JWT_SECRET` 时启动即失败（T0-R 已修，本轮未回退） |

## 5. 前端路由守卫（无头 Edge 真实渲染，不是 curl）

三种情形分别跑，判定依据是 DOM 里出现 `class="login-card"`（登录页）还是 `class="greet"`（概览页）：

| 情形 | 访问 | 结果 |
|---|---|---|
| 无令牌 | `/dashboard`、`/profile`、`/tasks`、`/jobs` | 4 个全部落到登录页，`greet` 计数 0 |
| 有有效令牌（正向对照） | `/dashboard` | 渲染概览页，DOM 里出现刚注册的用户名 `gt203751260` |
| 伪造/失效令牌 | `/profile` | 回到登录页，`greet` 计数 0 |

```
页面        退出码  字节    login-card  greet  判定
/dashboard  0      373618  2           0      重定向到登录页 ✓
/profile    0      373618  2           0      重定向到登录页 ✓
/tasks      0      373618  2           0      重定向到登录页 ✓
/jobs       0      373618  2           0      重定向到登录页 ✓
[guard] 失败数：0

[pos] /dashboard rc=0 bytes=386670 greet=1 login-card=0 用户名命中=gt203751260
[pos] 结论：带令牌渲染概览页 ✓

[exp] /profile 伪造令牌 rc=0 login-card=2 greet=0
[exp] 结论：失效令牌被清并回登录页 ✓
```

正向对照是必要的：只测「无令牌会跳登录」不能排除「所有页面都渲染登录页」这种坏情况，
所以额外用有效令牌证明概览页确实能出来。

## 7. 本轮自检发现并修复的缺陷

**`profileCompleted` 误报「已完善」**（提交 `72b9c0d`）

- 现象：`GET /api/stats/overview` 的 `profileCompleted` 只判 `user_profile` 有没有行。
- 触发路径：`PUT /api/profile` 是整体替换，用户只填手机号也会插入一行，于是概览页显示
  「已完善 · 学校专业已记录」，而学校专业一个都没填。
- 修复：SQL 改为 `school` 与 `major` 均非空（`TRIM` 后判空）。
- 反向验证：把 SQL 临时改回旧口径，`StatsControllerTest.phoneOnlyIsNotCompleted` 实测
  `JSON path "$.profileCompleted" expected:<false> but was:<true>` —— 用例确实抓得住这个缺陷，
  不是写了一个永远为真的断言。改回修复版后 4/4 通过。

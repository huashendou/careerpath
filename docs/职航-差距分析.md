> 对比对象：`项目开发指导/职航_CareerPath_项目整体介绍.docx`（17 章 / 8 表 / 约 7600 字，2026-11-15）

## 一、结论摘要

1. **功能覆盖率约 35%**：文档 8 个主模块 + 2 个补充能力中，2 项已具备、3 项部分具备、5 项完全没有。
2. **数据模型覆盖率 8/18 张表**，但其中 3 张语义要变。文档说的是「用户录入的真实岗位」，我们现在是「三类岗位模板」——**这是最容易返工的一处，必须先分层**。
3. **技术栈与文档第八节冲突**：文档要求 Java Spring Boot 作主后端、FastAPI 只作分析服务；现在是 FastAPI 单栈。本机 **JDK 25 已装，Maven / Gradle 均无**。
4. **匹配算法不冲突**：文档公式 `Σ(Wi×Mi)/ΣWi` 与现有 `Σ(w×min(L,T))/Σ(w×T)`，在 `Mi = min(L,T)/T` 定义下数学等价。core-only 口径可以原样保留。
5. **现有代码不白做**：`matching.py` / `resume.py` / `catalog.py` 正好对应文档里「智能分析服务」的职责，可作为分析服务复用。

### 4.3 关键概念冲突：现有「岗位」与文档「岗位」不是一回事

这是本次比对最重要的发现，直接决定要不要动现有 86 条数据。

| | 现有 `jobs` | 文档 `job_position` |
|---|---|---|
| 是什么 | **岗位类型模板**：前端开发 / Java 后端 / 数据分析 | **一条真实招聘信息**：某公司某岗位 |
| 来源 | `data/jobs.json` 预置 | 用户录入或粘贴 |
| 数量 | 3 条固定 | 用户自己的 N 条 |
| 要求 | 86 条，带 core/plus 类型与权重 | 从 JD 解析，页面上可人工修正 |
| 算分 | `Σ_core(w×min(L,T)) / Σ_core(w×T)`，分母 255/294/292 | 文档未定分母口径 |

**如果把 `jobs` 改名成 `job_positions`，86 条预置要求、core 权重 79/89/83、分母 255/294/292、以及 91 项测试里所有断言会一起失效。**

建议的两层结构：

```
job_templates（原 jobs，保留）         job_positions（新）
  ├─ 3 条预置模板                        ├─ 用户录入的真实岗位
  ├─ job_requirements（86 条，带权重）    ├─ 可空外键 template_id → job_templates
  └─ 用于「按岗位类型估算」               └─ job_position_skills（解析结果，可人工修正）
```

算分时：有 `template_id` 走模板权重（现有 core-only 口径）；纯实例岗位则按解析结果生成权重，或只做「已具备/待提升/缺证据」清单不打分。**这条规则文档没写，必须补。**

## 六、技术栈：三条路径

### 环境实测（2026-11-15 16:25）

| 项 | 状态 |
|---|---|
| JDK | ✅ 25.0.2 LTS，`JAVA_HOME=C:\Program Files\Java\jdk-25.0.2` |
| Maven | ❌ 未安装 |
| Gradle | ❌ 未安装 |
| Node 22 / npm 10 | ✅ 已装 |
| Python 3.14 / MySQL 9.0.1 | ✅ 已装 |

> JDK 25 属较新版本，Spring Boot 需 3.4+ 才完整支持；Lombok 等注解处理器可能在 JDK 25 上报错，需要实测。

### 路径 A：完全按文档（Java 主后端 + FastAPI 分析服务）

- **做什么**：新建 Spring Boot 服务，接管 auth / profiles / reports 等持久化与鉴权（约 11 个接口重写）；FastAPI 只保留 `catalog` + `analysis` + `resume` 共 6 个接口作分析服务。
- **代价**：11 个接口重写 + 双服务联调 + JWT 跨服务校验 + 「分析结果由 Java 持久化」带来的事务边界问题；还要先装 Maven。
- **收益**：符合文档「既定技术方向」；比赛材料里技术栈更完整（Java + Python 双语言）。
- **风险**：现有 91 项 pytest 中接口层测试要重写；前端 axios 的 baseURL 与错误处理要适配两套服务。

### 路径 B：保持 FastAPI 单栈

- **做什么**：全部新模块继续用 FastAPI + SQLAlchemy，文档第八节的 Java 部分记录为「已偏离」。
- **代价**：与文档明确要求冲突，需要在 `AGENTS.md` 记录偏离理由与确认人。
- **收益**：省掉 11 个接口重写与双服务联调；单服务事务简单；开发速度快约一倍。
- **风险**：如果这是竞赛作品且评审看重「Java 后端」，会丢分。

### 路径 C：先功能后技术栈（渐进迁移）

- **做什么**：先用 FastAPI 把 S1–S5 功能做出来，S6 前再评估是否补 Java 层。
- **代价**：后期迁移面更大（那时可能有 70+ 接口）。
- **收益**：先验证业务闭环能否跑通，再决定技术投入。
- **风险**：容易一直拖着不迁，最后与文档要求差距更大。

## 九、需要裁决的 5 个问题

1. **岗位模型**：是否接受「模板（3 类预置）+ 实例（用户录入）」两层结构？不接受则 86 条要求和 core-only 算分要推倒。
2. **技术栈**：A 完全按文档（Java 主后端）／B 保持 FastAPI 单栈／C 先功能后迁移？
3. **算分口径**：实例岗位（用户录入的真实 JD）没有权重时，是「按解析结果自动生成权重」，还是「只出清单不打分」？
4. **证据参与算分的力度**：`Mi` 里证据只作为「展示信息」不影响分数，还是真正乘一个证据系数？（后者会改变现有全部分数）
5. **范围优先级**：S1–S7 全做，还是先做 S1+S3（求职工作台 + 证据链）这两块最容易在演示中体现差异的？

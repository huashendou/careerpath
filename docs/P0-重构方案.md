## 二、目标架构

```
┌─────────────────┐   /api (8080)   ┌──────────────────────┐
│ Vue 3 + Element │ ──────────────► │ Java Spring Boot     │
│ + Vite :5173    │                 │ MyBatis-Plus         │
└─────────────────┘                 │ Spring Security+JWT  │
                                    └───────┬──────────────┘
                                            │ 内部 HTTP（X-Internal-Token）
                                            ▼
                                    ┌──────────────────────┐
                                    │ Python FastAPI :8000 │
                                    │ JD 解析 / 技能标准化 │
                                    │ 匹配与差距计算       │
                                    └───────┬──────────────┘
                                            ▼
                                      MySQL 9.0 `career_path`
```

| 服务 | 端口 | 职责 | 鉴权 |
|---|---|---|---|
| `backend-java` | 8080，前缀 `/api` | 用户、公司、岗位、投递、技能、证据、任务、面试、报告、统计分析 | JWT（Spring Security） |
| `analysis-service` | 8000，前缀 `/internal` | 岗位文本解析、技能标准化、匹配打分、差距与解释、统计聚合 | `X-Internal-Token` 共享密钥，不对公网暴露 |
| `frontend` | 5173 | 9 个页面，`/api` 代理到 8080 | localStorage 存 JWT |

**硬约束**
- 前端**只**访问 Java，不得直连 Python 分析服务。
- 分析结果必须由 Java 落库，并记录 `algorithm_version`。
- Python 服务不持有用户会话，不做鉴权业务，只接收结构化入参。

## 五、匹配口径（可解释，需在 T4 定稿并测试）

```
required_score = Σ_required(Wi × Mi) / Σ_required(Wi) × 100
bonus_score    = Σ_bonus(Wi × Mi)    / Σ_bonus(Wi)    × 100
Mi = 0.7 × (level / 5) + 0.3 × (evidence_completeness / 100 × relevance / 100)
     无证据时证据项记 0，Mi = 0.7 × (level / 5)
evidence_coverage = 已挂证据的 required 技能数 / required 技能总数
```

- **必备与加分分开出分**，不合并成一个总分（《整体介绍》第十节 2）。
- 分数只作辅助分析，UI 必须同时给出「为什么」：命中项、缺口项、缺证据项、Top 3 优先补强。
- 权重 `Wi` 与 `target_level` 由 JD 解析 + 用户人工修正产生，必须可追溯。
- 该公式中 0.7/0.3 为初始值，T4 需用样本标定并在报告里写明 `algorithm_version`。

## 十、v1 资产与 v2 的关系

- v1 的 `dev` 分支停在 R1「有条件通过」，**不再合并 main**，作为历史基线保留。
- v1 已通过的算分口径（core-only、anyOf、空轴 null）作为 v2 匹配算法的**回归参照**：v2 必须能解释为什么同一画像在 v1/v2 下分数不同。
- v1 的评审记录与问题（重复 skillId→500、旧进程自测）在 v2 重写时不得复现。
